Rules & Conventions

The non-negotiable engineering principles and conventions for this project. Every contribution — human or agent — follows these.

▶ The wiki protocol

Read before, update after, commit after.

  1. Before starting any task, read this page and the wiki page(s) for the area you will touch (e.g. Mapper before editing the mapper).
  2. After finishing, update those pages so they match the new reality. The wiki is the source of truth; stale documentation is a bug.
  3. When you add or change an agent, table, command, or convention, update both the specific page and any index that lists it (Agents, Commands, Data Model).
  4. Commit the change (and its wiki update) before moving on — see Git below. A task isn't done until it's committed.

Test-Driven Development (TDD)

  • Write tests first, then implement. Every new function or class has corresponding tests in tests/.
  • Tests run fully offline — mock all HTTP and LLM calls (respx for outbound HTTP; httpx ASGITransport for in-process FastAPI; no live Ollama).
  • Run the full suite with uv run pytest -v before committing.

Object-Oriented Programming (OOP)

  • Business logic lives in classes. Pure module-level functions are reserved for stateless utilities (e.g. score_document, parse_llm_response).
  • New agents follow the existing pattern: a class for the lifecycle (e.g. Mapper), main() as the CLI entry point, pure functions for stateless logic.

Human-Readable Code

  • Descriptive names: fetch_unscored_documents, not _fetch_docs.
  • Short, focused methods — one responsibility, < 30 lines as a guide.
  • No clever one-liners; prefer explicit over implicit.
  • Avoid abbreviations unless domain-standard (e.g. doc_id, iso).

Documentation

  • Every public class and public method has a docstring.
  • Class docstring: what it does and its role in the pipeline.
  • Method docstring: what it does, what it returns, and any side effects.
  • And — per the protocol above — the relevant wiki page is updated too.

Git — commit after every relevant change

Committing is part of finishing a task, not an afterthought. The moment a change is complete and its wiki page is updated, commit it — then push so the remote is a real backup.

  • Commit after each relevant change — a working feature, a fix, or a doc/wiki update — with a clear message. Don't let uncommitted work pile up.
  • Push regularly. The 4-week loss happened because work lived only locally and was never pushed. The remote is the backup.
  • Branch off main before committing if you're on the default branch.
  • Bundle the code change and its wiki update in the same commit so they never drift.
