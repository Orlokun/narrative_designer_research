Location Manager Ag-4 Real

The spatial twin of the Cast Manager: reads verified documents and catalogues the places where events happen — a flour factory in Temuco, a minister's house, La Moneda — with descriptions, appreciations, events and hard data per location, and feeds places back into the Propositor as location research missions.

Entry point: pipeline/location_manager/__init__.py → main() · CLI: location-manager run / enrich / analyze / score / status

What it does

  • Extraction (run): mines verified+mapped documents (chunked like the Cast Manager, so long memos lose nothing) for named places — kind ∈ building / factory / residence / city / region / street / office / other — and per-place facts: description (physical/objective), appreciation (a subjective opinion, with reported_by when stated), event (something that happened there) and data (address, capacity, output). Each processed document is stamped locations_extracted_at (idempotent, self-terminating).
  • Coreference: exact normalised match plus multi-token subsequence ("La Moneda" ⊂ "Palacio de La Moneda"), but single-token names match only exactly — "Temuco" the city never collapses into "Fábrica de harina de Temuco". Ambiguity never merges.
  • Character link: a place tied to a person ("casa de Salvador Allende") resolves the name against the cast roster and stores locations.character_id.
  • External grounding (enrich + analyze): same two-step as characters. enrich links each place to its Wikidata QID + Wikipedia article (Gatekeeper, stamped wikidata_checked_at). analyze mines the links — Wikidata claims give GPS coordinates (P625 → latitude/longitude), inception date (P571), architect (P84) and administrative territory (P131) as data facts; the Wikipedia article (Gemma) yields a one-paragraph description plus architectural data and trivia. Stamps wikidata_analyzed_at / wikipedia_analyzed_at; failures leave no stamp and retry next run.
  • Image gallery: analyze also harvests images into location_images — the Wikidata P18 images (up to 6, served as Commons Special:FilePath thumbnails) and the Wikipedia article's lead image (the pageimages prop rides along the same extract fetch — no extra request). Deduped by normalised filename, so the P18 image and the article's copy of it store once; each row keeps the Commons File: page for licence/attribution. Shown as the Galería on the admin detail (hot-linked from Commons — needs connectivity to render).
  • Research loop: thin locations are flagged needs_research; the Propositor mints kind='location' missions with kind-flavoured queries (a building searches arquitectura planos historia, a factory industria producción …). Harvested documents carry seed_location_id and are force-attributed to their seed on the next extraction pass — the same closed loop as characters, bounded by should_research (< 0.85, max 5 attempts, 3-day cooldown).

Completeness (strict, location flavour)

compute_location_completeness(): documentary base 0.25 (mentions/4) + facts 0.30 (facts/6) + external linking 0.30 (Wikidata 0.15 + Wikipedia 0.15; linked-only 0.07 each) + coordinates 0.15 (the GPS datum the game needs). Hard gate: neither source analyzed → ≤ 0.60. Complete = ≥ 0.85. Breakdown persisted in completeness_detail; bulk re-score via location-manager score.

Place in the flow

Runs after the Mapper, alongside the Cast Manager — both mine the same verified+mapped documents with independent stamps. Under make pipeline the chain runs run → enrich (50) → analyze (10) and records location_manager / location_analyze stages against the run id.

CLI

uv run location-manager run [--batch 50] [--all]
uv run location-manager enrich [--limit 100]    # link Wikidata/Wikipedia (Gatekeeper)
uv run location-manager analyze [--limit 30] [--no-llm]  # GPS, architect, article
uv run location-manager score                   # bulk re-score
uv run location-manager status
